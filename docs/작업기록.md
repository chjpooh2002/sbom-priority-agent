### 2026-11-02 · 빌드 환경을 JDK 17 + Gradle 7.6.4로 고정
- 상황: `scan.sh`가 시스템 `gradle`에 의존했는데 설치돼 있지 않았고, `sample-app`에 `gradlew`도 없었다. PATH 기본 JDK는 21인데, JDK 21을 지원하는 Gradle(8.5 이상)은 Spring Boot 2.6.5 플러그인 지원 범위(7.x까지)를 벗어난다.
- 판단: (1) Gradle 7.6.4 + JDK 17로 맞추기, (2) 최신 Gradle + JDK 21로 가되 Boot 버전 올리기, (3) 1번에 `gradlew`까지 커밋하기, 셋을 비교했다. 2번은 일부러 고정한 취약 의존성이 바뀌어 측정 대상이 달라지므로 제외했다. 다른 환경에서도 같은 빌드가 나오도록 3번을 골랐다. JDK 경로는 사람마다 다르므로 저장소에 쓰지 않고, `scan.sh`에서 주 버전만 확인해 17이 아니면 멈추게 했다.
- 변경: `sample-app/gradlew`, `sample-app/gradlew.bat`, `sample-app/gradle/wrapper/*`, `scripts/scan.sh`, `README.md`, `.gitattributes`(CRLF 변환으로 `gradlew`·`*.sh`가 깨지지 않게 LF 고정)

### 2026-11-02 · 직접 사용 판정을 실행 jar 클래스 색인 방식으로 변경
- 상황: `reach.py`는 Java 패키지 이름이 지정되지 않은 라이브러리에 메이븐 그룹 아이디를 접두어로 썼다. 그래서 `org.springframework`로 시작하는 import가 모두 spring-core·spring-context·spring-expression의 직접 사용으로 잡혔고, spring-boot와 spring-boot-autoconfigure는 서로의 import가 잡혔다. log4j-core는 log4j-api와 같은 접두어를 써서 API 클래스 import가 core 사용으로 잡혔다.
- 판단: (1) 패키지 이름표를 보강하고 가장 긴 접두어만 인정하기, (2) 빌드된 실행 jar 안 라이브러리의 클래스 색인으로 import를 연결하기, (3) 그룹 아이디 대체를 없애기, 셋을 비교했다. 1번은 손으로 관리하는 표라 다른 프로젝트에서 또 빠지는 항목이 생기고, 3번은 표에 없는 라이브러리를 놓친다. "import한 클래스가 실제로 들어 있는 라이브러리"라는 일반 원칙이고 스캔 대상과 같은 jar를 쓰는 2번을 골랐다. 정답 작성 전이고 정답 파일은 보지 않았다. jar가 없으면 예전 접두어 방식으로 돌아가고, 어느 방식을 썼는지 `scan_meta.json`의 `reach_method`에 남긴다. 겸해서 Windows에서 경로 구분자가 `\`로 찍히던 것도 `/`로 통일했다.
- 변경: `src/sbom_agent/reach.py`, `src/sbom_agent/cli.py`(`reach_method` 기록), `eval/make_sheet.py`(머리말 문구), `eval/gold30_sheet.md`(다시 생성)
- 결과: 직접 사용 라이브러리가 9종에서 5종으로 줄었다(commons-text, log4j-api, spring-boot, spring-boot-autoconfigure, spring-web). 132건 중 규칙 판정이 바뀐 건 19건이다(내용은 확인하지 않음). 심각도 점수만 방식은 바뀌지 않았다. fixtures 확인과 jar가 없을 때의 대체 동작을 확인했다.
