# 작업기록

### 2026-11-02 · 빌드 환경을 JDK 17 + Gradle 7.6.4로 고정
- 상황: `scan.sh`가 시스템 `gradle`에 의존했는데 설치돼 있지 않았고, `sample-app`에 `gradlew`도 없었다. PATH 기본 JDK는 21인데, JDK 21을 지원하는 Gradle(8.5 이상)은 Spring Boot 2.6.5 플러그인 지원 범위(7.x까지)를 벗어난다.
- 판단: (1) Gradle 7.6.4 + JDK 17로 맞추기, (2) 최신 Gradle + JDK 21로 가되 Boot 버전 올리기, (3) 1번에 `gradlew`까지 커밋하기, 셋을 비교했다. 2번은 일부러 고정한 취약 의존성이 바뀌어 측정 대상이 달라지므로 제외했다. 다른 환경에서도 같은 빌드가 나오도록 3번을 골랐다. JDK 경로는 사람마다 다르므로 저장소에 쓰지 않고, `scan.sh`에서 주 버전만 확인해 17이 아니면 멈추게 했다.
- 변경: `sample-app/gradlew`, `sample-app/gradlew.bat`, `sample-app/gradle/wrapper/*`, `scripts/scan.sh`, `README.md`, `.gitattributes`(CRLF 변환으로 `gradlew`·`*.sh`가 깨지지 않게 LF 고정)
- 결과: JDK 17에서 빌드·스캔 성공(약 2분 30초, grype DB 첫 다운로드 포함). SBOM 구성 요소 35개, grype 매칭 132건. JDK 21일 때는 안내 문구를 출력하고 exit 1로 멈추는 것을 확인했다. 사용 도구는 syft 1.54.1, grype 0.121.0(DB 2026-11-01 빌드)이다.

### 2026-11-02 · 보고서 출력 코드의 Python 3.11 문법 오류 수정
- 상황: `cli.py` 보고서 표에서 f-string 안에 같은 따옴표를 쓰는 중첩 f-string이 있었다(3.12 이상에서만 허용). Python 3.11.9에서 모듈을 불러오는 단계에서 SyntaxError가 나서 `run` 자체가 실행되지 않았다.
- 판단: Python 3.12를 설치하는 대신 코드를 고쳤다. 고칠 곳이 한 줄이고, 최소 버전 표기가 없어 다른 환경에서도 같은 문제가 날 수 있기 때문이다. 중첩 f-string을 `format(r['epss'], '.3f')`로 바꿨고, 판정 로직은 건드리지 않았다.
- 변경: `src/sbom_agent/cli.py`
- 결과: `--no-agent` 실행 성공. 132건, 라이브러리 21종. EPSS는 132건 모두 실제 값으로 채워졌다(fixtures 미사용).

### 2026-11-02 · EPSS 캐시 이름 고정과 측정 입력 스냅샷 저장
- 상황: EPSS 캐시 파일 이름을 `hash(tuple)`로 정하고 있었다. 이 값은 실행할 때마다 바뀌어서 캐시가 한 번도 재사용되지 않았다. 또 측정에 쓴 외부 지표와 도구·DB 버전이 남지 않아, 나중에 같은 결과를 다시 만들 수 없었다.
- 판단: 캐시 이름은 CVE 목록의 sha256 앞 16자리로 정했다. 내용이 같으면 이름도 같다. 스냅샷은 기존 `--kev-file`, `--epss-file` 형식과 같게 저장해, 새 옵션 없이 그대로 다시 넣어 재현할 수 있게 했다. syft 버전은 같은 폴더의 `sbom.cdx.json`에서 읽는다.
- 변경: `src/sbom_agent/enrich.py`(`enrich`가 사용한 원본 지표를 반환), `src/sbom_agent/cli.py`(`run`이 `out/kev_snapshot.json`, `out/epss_snapshot.json`, `out/scan_meta.json`을 저장)
- 결과: 두 번째 실행부터 캐시 파일이 새로 생기지 않는 것을 확인했다. 수정 전 결과와 비교해 EPSS와 규칙 판정이 바뀐 건은 0건이다. `--offline`으로 스냅샷만 넣어 다시 돌린 `results.json`이 원래 결과와 같았다. 측정 입력은 grype DB 2026-11-01T06:20:12Z 빌드, KEV 2026.10.30, EPSS 2026-11-01 기준이다. `out/`은 gitignore 대상이라 스냅샷은 제출 전에 따로 보관해야 한다.

### 2026-11-02 · 정답 작성용 사실 표(gold30_sheet.md) 생성
- 상황: 정답을 매기려면 건마다 CVSS·EPSS·KEV·수정 버전·코드 사용 위치·설명을 찾아봐야 한다. 그런데 `results.json`과 `report.md`에는 판정이 섞여 있어 볼 수 없다.
- 판단: 스크립트가 `results.json`을 읽지 않고, `grype.json`과 측정 스냅샷으로 `load_grype → enrich → annotate`만 다시 돌리게 했다. `apply_rules`를 부르지 않으므로 판정이 섞일 길이 없다. 라이브러리별 사용 방식은 빌드 파일, 코드, 설정, `gradlew dependencies` 결과로 확인한 사실만 `eval/library_notes.json`에 따로 적었다. GHSA 대표 항목은 설명이 제목 한 줄뿐이라, 연관 항목까지 보고 가장 긴 설명을 썼다. 에이전트 입력(`load_grype`)은 바꾸지 않았다.
- 변경: `eval/make_sheet.py`, `eval/library_notes.json`, `eval/gold30_sheet.md`
- 결과: 30건, 21종. P1~P4 표기는 README 기준표에만 있다. 작성 중 두 가지를 발견했다. 첫째, `reach.py`가 그룹 아이디를 패키지 접두어로 쓰면서 과잉 매칭한다(spring-core·spring-context·spring-expression, spring-boot와 spring-boot-autoconfigure, log4j-core). 이번에는 고치지 않고 시트에 사실대로 적었다. 둘째, 클래스패스에 log4j-core와 log4j-to-slf4j가 함께 있어, 어느 구현이 쓰이는지 저장소 파일만으로는 확정할 수 없다.

### 2026-11-02 · 에이전트 부분 실행(--keys)과 측정 지표 추가
- 상황: 기존 비교표는 정확도 세 가지와 경보 건수만 보여 줬다. 에이전트가 판정을 바꿔서 실제로 나아졌는지, 근거가 진짜인지, 비용이 얼마인지는 알 수 없었다. 또 정답은 30건만 매기는데 에이전트는 132건을 전부 돌려야 했다.
- 판단: `--keys`로 지정한 건만 에이전트로 판정하고, 상태를 `agent_status`(ok/failed/skipped)로 구분했다. 실패와 대상 외 건을 섞어 세지 않기 위해서다. 근거 검증은 evidence의 `경로:줄번호`가 분석 대상 폴더 안에 있고 그 줄이 실제로 있는지만 본다. 줄의 내용이 주장과 맞는지는 보지 않으므로 상한 지표다. "정답에 가까워짐/멀어짐"은 P1~P4 거리로 셌다. 경보 감소율은 정답과 무관하게 전체 132건 기준으로 셌다. 이전 형식의 `results.json`도 읽을 수 있게 했다.
- 변경: `src/sbom_agent/agent.py`(건별 시간·토큰 반환), `src/sbom_agent/cli.py`(`run --keys`, `results.json`에 `agent_status`·`agent_seconds`·`agent_usage` 추가, `eval`에 경보 감소·에이전트 지표·`--src` 추가), `README.md`
- 결과: fixtures로 `run --no-agent`와 `eval`이 정상 동작했다. 가짜 에이전트 결과(성공 2, 실패 1, 대상 외 2)로 실패율, 바뀐 건수, 근거 검증률(4/8, 폴더 밖 경로와 없는 줄은 제외), 평균 시간·토큰이 손 계산과 일치했다. 가짜 정답과 가짜 결과는 scratchpad에서만 썼다. 실제 측정값은 아직 없다.

### 2026-11-02 · 직접 사용 판정을 실행 jar 클래스 색인 방식으로 변경
- 상황: `reach.py`는 Java 패키지 이름이 지정되지 않은 라이브러리에 메이븐 그룹 아이디를 접두어로 썼다. 그래서 `org.springframework`로 시작하는 import가 모두 spring-core·spring-context·spring-expression의 직접 사용으로 잡혔고, spring-boot와 spring-boot-autoconfigure는 서로의 import가 잡혔다. log4j-core는 log4j-api와 같은 접두어를 써서 API 클래스 import가 core 사용으로 잡혔다.
- 판단: (1) 패키지 이름표를 보강하고 가장 긴 접두어만 인정하기, (2) 빌드된 실행 jar 안 라이브러리의 클래스 색인으로 import를 연결하기, (3) 그룹 아이디 대체를 없애기, 셋을 비교했다. 1번은 손으로 관리하는 표라 다른 프로젝트에서 또 빠지는 항목이 생기고, 3번은 표에 없는 라이브러리를 놓친다. "import한 클래스가 실제로 들어 있는 라이브러리"라는 일반 원칙이고 스캔 대상과 같은 jar를 쓰는 2번을 골랐다. 정답 작성 전이고 정답 파일은 보지 않았다. jar가 없으면 예전 접두어 방식으로 돌아가고, 어느 방식을 썼는지 `scan_meta.json`의 `reach_method`에 남긴다. 겸해서 Windows에서 경로 구분자가 `\`로 찍히던 것도 `/`로 통일했다.
- 변경: `src/sbom_agent/reach.py`, `src/sbom_agent/cli.py`(`reach_method` 기록), `eval/make_sheet.py`(머리말 문구), `eval/gold30_sheet.md`(다시 생성)
- 결과: 직접 사용 라이브러리가 9종에서 5종으로 줄었다(commons-text, log4j-api, spring-boot, spring-boot-autoconfigure, spring-web). 132건 중 규칙 판정이 바뀐 건 19건이다(내용은 확인하지 않음). 심각도 점수만 방식은 바뀌지 않았다. fixtures 확인과 jar가 없을 때의 대체 동작을 확인했다.
