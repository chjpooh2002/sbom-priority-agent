# 오픈소스 취약점 조치 우선순위 에이전트

취약점 스캐너는 수십~수백 건의 경보를 쏟아내지만, 그중 이 서비스에 실제로 위험한 것은 일부다.
이 프로젝트는 스캔 결과를 받아 **실제로 급한 것만 위로 올리고, 고칠 방법까지 붙여 주는** 에이전트다.

## 구조

```
빌드 결과물(jar)
  → 구성 요소 목록(SBOM) 생성 ·········· syft
  → 알려진 취약점 대조 ·················· grype
  → 외부 지표 보강 ······················ 악용 가능성 점수(EPSS), 실제 악용 확인 목록(CISA KEV)
  → 코드 사용 여부 ······················ 우리 코드가 해당 라이브러리를 직접 가져다 쓰는지
  → 1차 규칙 판정 ······················· 숫자로 정할 수 있는 건 언어 모델에 맡기지 않는다
  → 2차 에이전트 판정 ···················· 코드·설정을 직접 읽어 공격 경로 확인, 근거 있을 때만 판정 조정, 조치안 작성
  → 보고서 + 판단 근거 기록
```

설계 원칙

1. **역할 분리**: 점수 계산은 규칙이, 맥락 판단(프레임워크 내부 사용, 공격 전제 조건 성립 여부, 입력 흐름)은 에이전트가 맡는다.
2. **근거 강제**: 에이전트는 정해진 출력 형식으로만 답하고, 판정을 바꿀 때는 파일 경로와 줄 번호를 근거로 남겨야 한다.
3. **측정 가능**: 사람이 먼저 매긴 정답과 비교해 세 방식(심각도 점수만 / 규칙 / 규칙 + 에이전트)의 정확도를 같은 표로 낸다.
4. **안전한 도구**: 에이전트는 프로젝트 폴더 안 파일을 읽기만 할 수 있다.

## 실행

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
brew install syft grype            # 윈도우는 각 도구 배포 페이지 참고
export JAVA_HOME="/c/Program Files/Eclipse Adoptium/jdk-17.0.16.8-hotspot"   # JDK 17 필요 (윈도우 Git Bash 예시, 경로는 설치 위치에 맞게)

# 1) 스캔
bash scripts/scan.sh sample-app out

# 2) 규칙 판정만 먼저 (API 키 불필요)
PYTHONPATH=src python -m sbom_agent.cli run --scan out/grype.json --src sample-app --out out --no-agent

# 3) 정답 표 작성: 결과 파일을 보기 전에 직접 판단해서 채운다
PYTHONPATH=src python -m sbom_agent.cli gold --results out/results.json --out eval/gold.csv

# 4) 에이전트까지 실행
export OPENAI_API_KEY=...
export OPENAI_MODEL=...            # 사용할 모델 이름
PYTHONPATH=src python -m sbom_agent.cli run --scan out/grype.json --src sample-app --out out
#   정답을 매긴 건만 에이전트로 판정하려면 --keys eval/gold30.csv 를 붙인다(나머지는 규칙 판정 유지)

# 5) 정확도 비교
PYTHONPATH=src python -m sbom_agent.cli eval --results out/results.json --gold eval/gold.csv --out eval/result_새이름.md
#   이미 있는 결과 파일(1차 기록 eval/result.md 등)은 --force 없이는 덮어쓰지 않는다
```

## 예제 서비스 (`sample-app/`)

측정용으로 오래된 의존성을 일부러 고정한 스프링 부트 서비스다. 배포하지 않는다.

| 상황 | 의도 |
| --- | --- |
| 요청 헤더를 그대로 로그에 기록 | 직접 사용 + 외부 입력 도달 |
| 사용자 입력을 문자열 치환기에 전달 | 직접 사용 + 외부 입력 도달 |
| 요청 값을 객체에 바인딩, jar 형태로 실행 | 프레임워크 내부 사용, 공격 전제 조건 일부 불성립 |
| 선언만 하고 쓰지 않는 라이브러리 | 심각도는 높지만 실제 위험은 낮음 |
| 개발용 데이터베이스, 웹 콘솔 꺼짐 | 설정으로 공격 경로 차단 |

의존성별 의도 (출제 의도는 여기에만 적고 `sample-app/` 안에는 주석으로 남기지 않는다. 에이전트가 읽는 파일에 정답 힌트가 섞이지 않게 하기 위해서다.)

| 의존성 | 의도 |
| --- | --- |
| spring-boot-starter-web 2.6.5 | spring-beans 5.3.17, snakeyaml 1.29, jackson 2.13.x, 내장 Tomcat 9.0.60 이 함께 들어온다 |
| log4j-core / log4j-api 2.14.1 | 코드에서 사용자 입력(요청 헤더)을 직접 로그에 기록한다 |
| commons-text 1.9 | 코드에서 사용자 입력으로 문자열 치환을 한다 |
| commons-collections 3.2.1 | 선언만 하고 코드에서 쓰지 않는다 |
| h2 1.4.200 (runtimeOnly) | 로컬 개발용이며 웹 콘솔은 꺼져 있다 |

## 판정 기준

정답 작성, 규칙 판정, 에이전트 지시문이 모두 아래 기준 하나를 쓴다. 에이전트 지시문은 이 구간을 그대로 읽어 간다(`src/sbom_agent/criteria.py`).
`eval/gold30.csv`(1차 정답)는 이 기준을 README 에 적기 전에 매긴 것이다.

<!-- criteria:start -->
판정은 라이브러리 단위가 아니라 취약점 단위로 한다. 아래 질문을 순서대로 묻고, 처음 "아니오"가 나온 곳에서 등급을 정한다.

1. 실행 중 로드되는가: 우리 코드든 프레임워크든, 서비스가 실행될 때 이 라이브러리의 코드가 실제로 쓰이는가.
2. 취약한 기능이 켜져 있는가: 취약점이 있는 그 기능 자체를 쓰거나 켜 두었고, 취약점 설명에 적힌 공격 전제 조건(설정, 실행 환경, 배포 형태)이 이 서비스에서 성립하는가.
3. 외부 입력이 닿는가: 외부 요청 값이 그 취약한 기능까지 흘러가는가.
4. 쉽게 터지는가: 실제 악용 목록(KEV)에 있거나, 인증 없이 원격에서 쉽게 악용할 수 있는가.

| 결과 | 등급 | 조치 |
| --- | --- | --- |
| 1 이 아니오 | P4 낮음 | 기록만 |
| 2 또는 3 이 아니오 | P3 보통 | 정기 업데이트 때 |
| 4 가 아니오 | P2 높음 | 다음 배포에 포함 |
| 모두 예 | P1 긴급 | 이번 주 조치 |

"라이브러리가 요청 경로에 있다"는 2 의 근거가 아니다. 2 는 취약한 기능 자체가 쓰이는지를 묻는다.
- 예: Jetty 서버가 모든 요청을 받더라도, 특정 커넥터 기능의 취약점은 그 커넥터 기능을 켰을 때만 2 가 "예"다.
- 예: XStream 이 클래스패스에 있어도, 외부에서 받은 XML 을 객체로 바꾸는 기능에 넣을 때만 2 가 "예"다.

"우리 코드가 직접 가져다 쓰지 않음"은 1 의 "아니오"가 아니다. 프레임워크가 내부에서 쓰면 1 은 "예"다.
1 을 "아니오"로 하려면 실행 중 로드되지 않는다는 근거(실행 파일에 없음, 해당 기능을 켜는 설정이 없음 등)가 있어야 한다.

## 결과

상세 결과는 `eval/result_final.md`, 정답이 바뀐 내역은 `eval/gold_changes.md`, 실행 확인 기록은 `eval/fact_checks.md`에 있다.
같은 판정 결과를 두 정답으로 채점했다. 정답 v1은 처음 매긴 것이고, 정답 v2는 위 판정 기준과 실행 확인 결과를 다시 적용해 고친 것이다.

검증 세트 15건(개선에 쓰지 않은 세트)

| 방식 | 정확히 일치 v1 → v2 | 한 단계 이내 v1 → v2 | 급한 건 놓치지 않은 비율 v1 → v2 | 불필요한 긴급 경보 v1 → v2 |
| --- | --- | --- | --- | --- |
| 심각도 점수만 | 20% → 13% | 73% → 80% | 67% (4/6) → 측정 불가 | 5 → 9 |
| 규칙 | 47% → 60% | 73% → 80% | 33% (2/6) → 측정 불가 | 3 → 5 |
| 규칙 + 에이전트 (gpt-6-luna) | 47% → 60% | 67% → 100% | 17% (1/6) → 측정 불가 | 2 → 3 |
| 규칙 + 에이전트 (gpt-6-sol) | 53% → 67% | 67% → 100% | 17% (1/6) → 측정 불가 | 1 → 2 |

경보 감소(132건 전체, 정답과 무관): 심각도 점수만으로 판정하면 P1·P2가 76건이다. 규칙은 이를 29건으로 줄였고(62% 감소), 규칙 + 에이전트(gpt-6-luna)는 14건으로 줄였다(82% 감소).
에이전트 비용은 건당 luna $0.0024, sol $0.0374이고, 132건 전체를 luna로 판정하면 $0.32다. 132건에서 실패는 0건이다.

결과를 읽을 때 주의할 점
- 규칙과 에이전트는 경보를 크게 줄이고 정확히 일치하는 비율도 높였다. 하지만 **급한 건을 놓치는 경향**이 있다. gold30(개선에 쓴 세트, 참고용)에서 급한 건을 놓치지 않은 비율은 정답 v2 기준으로 심각도 점수만 58%, 규칙 42%, luna 17%, sol 8%다.
- **정답 v2는 v1 결과를 본 뒤에 고쳤다.** 근거는 실행 확인과 취약 기능 사용 여부지만, 결과를 모르는 상태에서 매긴 정답이 아니다. 그래서 v2의 수치 상승을 개선 효과의 근거로 쓰기는 어렵다.
- **검증 세트 v2에는 급한 건(P1·P2)이 0건이다.** 그래서 v2로는 놓친 비율을 잴 수 없다. 정답이 모두 P3·P4이므로 등급을 낮게 매기는 쪽이 정확도에서 유리하다.
- 실행 확인 결과, `sample-app`의 log4j API 호출은 log4j-core가 아니라 log4j-to-slf4j를 거쳐 logback이 처리한다. 의존성 표의 log4j-core 2.14.1 행에 적은 출제 의도("사용자 입력을 직접 로그에 기록한다")와 달리, 그 기록을 log4j-core가 처리하지 않는다.
- 판정은 한 번씩만 실행했다. 같은 입력을 다시 판정했을 때 45건 중 4건의 등급이 달랐다.

## 한계

- 코드 사용 여부는 가져오기 문장 기준이라, 리플렉션이나 설정만으로 쓰이는 경우는 에이전트 판단에 기댄다.
- 정답은 한 사람이 매긴 것이라 기준에 따라 달라질 수 있다.
- `fixtures/` 의 점수는 동작 확인용 가짜 값이다. 측정에는 실제 스캔 결과만 쓴다.
